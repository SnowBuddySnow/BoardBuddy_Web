# 시즌방 예약 개선

## 이번 변경

- 기존 크루 달력 컴포넌트와 색상 체계를 유지한다. 날짜를 한 번 선택하면 전체 월 달력을 유지한 채 모바일에서는 아래, PC에서는 오른쪽에 현황을 표시한다.
- 확정·대기 인원과 대기 순번을 구분한다. 기본 정렬은 확정 우선·대기 순번, 예약순은 예약 ID 오름차순이다. API에 신청 시간이 없으므로 ID 기준임을 명시한다.
- 정렬 선택의 텍스트/화살표 공간을 분리하고 여백과 불필요한 하단 공간을 줄인다.
- 시즌방 기능을 재활성화한다. 기본 운영 기간은 기존 신청 달력과 같은 10월~5월이며 이벤트도 함께 제공한다. 명시적 운영 모드 설정, 크루 접수 설정, 회원 상태, 권한과 서버 접수 기간 검사는 유지한다.
- 신청·취소 결과의 success를 확인한다. 실패를 성공으로 표시하지 않으며 대기 신청은 순번을 안내한다. 처리 중 중복 제출을 막는다.
- 상세 조회는 선택한 날짜에만 수행하고 15초 동안 재사용하며 진행 중 요청을 합친다. 신청·취소 후 월/일 정보를 갱신한다. 수동 새로고침을 제공한다. 이 캐시는 실시간 확정 수단이 아니며 실제 배정은 서버에서 결정한다.
- 서버는 전체 크루 예약 이력을 메모리에 불러오는 대신 해당 월의 확정 수만 DB에서 집계한다. 개인 표시도 해당 월·본인으로 제한하고 누적 횟수는 COUNT로 읽는다. 기존 인덱스를 사용하며 DB 스키마는 변경하지 않는다.
- 첫 예약 전의 빈 날짜는 조회만으로 빈 현황을 반환한다. GET으로 예약 날짜 행을 만들지 않는다.

## 참고한 방식과 다음 제안

Airbnb는 호스트가 정한 조건을 충족하는 이용자에게 별도 수락 없는 즉시 예약을 제공하고, 사전 통지·최소/최대 숙박 기간 등은 운영 설정으로 관리한다. 이에 근거한 **제안**은 승인된 크루원에게 정원 내 즉시 확정을 기본으로 제공하고, 예외만 운영자가 검토하는 것이다. 본인 확인과 크루 승인을 생략하자는 뜻은 아니다.
[Airbnb 공식 예약 설정 안내](https://www.airbnb.co.kr/help/article/484)

네이버는 예약 신청·확정·변경·취소 단계별 알림과 관리자/운영자에 대한 알림 제공을 안내한다. 이에 근거한 **제안**은 예약 상태와 입금 상태를 별도로 유지하면서 확정·대기 승격·취소 시 당사자에게 알리고 운영자는 필요한 변경만 받게 하는 것이다. 알림 발송 기능과 전달 보장은 이번 변경 범위가 아니다.
[네이버 스마트플레이스 공식 안내](https://new.smartplace.naver.com/notices/551)

### 부원 흐름

크루 홈 → 기존 달력에서 날짜 선택 → 확정/대기/정원 확인 → 신청 → 확정 또는 대기 순번 확인 → 내 예약에서 취소.

여러 날짜 신청은 기존 예약 화면을 사용한다. 이후에는 숙박 시작·종료일 선택과 전체 비용·규칙 확인을 한 화면에 연결하는 방식을 제안한다. 날짜별 배정이 일부만 성공할 수 있는 현재 계약을 숨기지 않아야 한다.

### 운영자 흐름

운영 센터 → 예약 관리 → 날짜별 확정/대기 조회 → 입금 상태·메모 수정 → 저장.

현재 서버의 정원 제한과 취소 시 대기 승격을 유지한다. 이후에는 대기 승격 알림, 변경 이력, 미입금 필터를 우선 제안한다. 미입금 자동 취소·노쇼 제재·우선순위 변경은 운영 정책을 결정한 뒤 도입한다.

## 검증과 운영 한계

단위 테스트와 합성 브라우저 시나리오로 한 번 선택, 읽기 전용 상태, 신청·취소 후 갱신, 실패 응답, 중복 제출과 반응형을 확인한다. 백엔드 MySQL 통합 테스트는 과거 데이터가 있는 월 조회 시 예약 엔티티를 적재하지 않는지, 병렬 조회 100건, 정원 2명에 동시 신청 10건과 첫 대기자 승격을 확인한다.

이는 로컬 재현 검증이며 운영 최대 동시 사용자 수를 보장하지 않는다. 실제 트래픽 목표를 정한 뒤 스테이징에서 응답 p95/p99, DB 커넥션 대기, 잠금 재시도, 오류율을 측정해야 한다. 공유 캐시·분산 큐·속도 제한은 그 결과와 다중 인스턴스 구성을 보고 도입한다. 개인·관리자 데이터를 공개 캐시에 저장하지 않는다.

백엔드 재활성화 후 프론트 변경을 배포한다. 서버의 SEASON_HOUSE_RESERVATIONS_ENABLED=false는 긴급 중단 수단으로 남는다. develop PR은 관리자가 병합하며 실제 스테이징 배포/로그인 여정 검증은 병합 후 진행한다.

## 메뉴·가독성 추가 개선

하단은 홈·시즌방·이벤트·내 크루의 최대 네 개로 제한하고, 내 정보와 알림은 모바일/PC 상단 계정 메뉴로 옮긴다. 내 예약은 시즌방 헤더에서 연결한다. 메뉴 표시만으로 권한을 부여하지 않으며 서버의 canManageReservations가 true인 경우에만 입금·관리자 메모 편집을 보여준다.

달력은 전체 월을 유지하고 모바일 날짜 행에 여유를 두되 큰 패널 여백은 늘리지 않는다. 혼잡도는 초록/주황/빨강과 날짜별 여유/보통/혼잡 문구를 함께 표시한다. 색만으로 정보를 전달하지 않는 접근성 원칙을 따른다.
[W3C Use of Color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)

신청·취소가 700ms 이상 진행되면 처리 대기창을 보여준다. 실제 요청 응답을 기다리는 상태이며 접속 대기열 순번이나 예상 시간을 만들어 표시하지 않는다. 다중 서버에서 정확한 접속 대기열을 제공하려면 공유 큐, 입장 토큰, 만료·재접속 정책, 공정성 기준과 운영 용량을 별도로 구현해야 한다.

마스코트 추천은 A 눈여우 버디(우선 추천), B 보드 타는 수달, C 눈뭉치다. 눈여우는 겨울 스포츠와 시즌방 열쇠를 연결하기 쉽고, 수달은 사계절 커뮤니티 확장에 적합하며, 눈뭉치는 작은 상태 아이콘으로 단순화하기 좋다. 네이비·하늘색·노란 포인트의 비교 시안은 검토용이며 제품에 자동 적용하지 않는다.
